# Anand and Susmita — Wedding Invitation

The Wedding project now also includes the Jothe Jotheyali guest and host features for **only Anand and Susmita's wedding**. The original invitation remains at `/`, with companion links below its existing footer. Start at `/invitation` for photos and wishes, `/rsvp` for family recovery, or `/admin` for hosts. There is no marketing page or event picker.

**Live setup:** follow [the Supabase and deployment guide](docs/SUPABASE-SETUP.md). Without Supabase environment variables, the companion uses browser-only demo data (PIN `291126`; any email/password for demo host sign-in).

**Family in the profile menu:** linked family guests find **Family RSVP** beneath **Wedding invitation** in their top-right account menu, including on the general invitation and Feed. Family is removed from the main navigation. Live `/rsvp`, `/e/...`, `/i/...` and `/app/...` pages require the existing Google sign-in gate before mounting family content; the OAuth callback preserves the destination and reclaims an existing linked family for the signed-in account. Google access alone does not create family membership; the existing invitation/PIN and member selection still apply. Existing email/password hosts retain access through the same gate. Local demo entry stays usable without a Google provider. This is a frontend entry requirement; existing database family invitation/PIN policies are unchanged. Run `npm.cmd run test:family-profile` for responsive menu and sign-in/return checks.

**Hosts & co-owners:** `/admin/hosts` (on mobile, **More → Hosts & co-owners**) lists the team. Owners can add a **Host** (`cohost`) or **Co-owner** (`owner`) by name/email and send a one-time password setup link. Co-owners may manage the team; hosts retain existing wedding administration privileges. Existing memberships are never silently promoted or overwritten by repeat invitations. **Send password link** sends a setup email for an unverified account or a recovery email for a verified host. Recipients open these links on their own device, then choose a password. Everyone can also use **Forgot password?** on host sign-in. The demo saves team records locally and explicitly sends no email. Apply `0017_host_team_management.sql`, deploy `host-team` and the existing `host-password-reset` functions, configure SMTP and the reset redirect, then deploy the frontend; see [host recovery setup](docs/HOST-PASSWORD-RECOVERY.md). Run `npm.cmd run test:hosts`, `npm.cmd run test:recovery`, and `npm.cmd run test:access` for mocked email/browser and local database verification.

**Four photo reactions:** the feed's **React** button opens a Facebook-style row of **Blessings (Akshate), Love, Wow and Celebrate**. Tap, press and hold on touchscreens, hover on desktop, or use the keyboard. Each account has one reaction per individual photo: choose another to replace it, or select the same reaction to remove it. Carousel counts and selections follow the active image. A successful reaction shows its matching rice shower, floating hearts, stars or confetti over that image; reduced-motion mode uses a brief static symbol. The picker stays within the viewport and above sticky navigation. Failed saves restore the previous choice and show an inline error. Existing blessings and the host's reaction totals are preserved. Apply **`0016_photo_reactions.sql`** after the prior migrations before deployment. Counts are aggregated in PostgreSQL, without exposing other guests' account IDs, and large image collections are requested in bounded batches. Run `npm.cmd run test:reactions`, `npm.cmd run test:access` and `npm.cmd run test:feed`; browser checks use mocked data. The picker follows the [WAI-ARIA menu button pattern](https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/).

**Guest emails and wedding memories:** **Admin → Analytics → Guest contacts & memories** lists verified Google guests by account ID, with their Google name/email, photo-post/image/wish counts, current reactions given, and recorded wedding activity/sign-in dates in IST. Search by name or email; **View memories** opens all of that guest's photo posts and wishes, with every carousel image, pending/hidden states and pagination. **Export all guests (CSV)** keeps the complete contact/activity summary; **Export all posts & wishes (CSV)** keeps all owned content, including records beyond the latest-20/feed limits. A guest's dialog also exports only their own content. Exports ignore the list search and include stable post/image IDs and private Storage paths, not expiring signed URLs. Open photos from the host memory view to save the actual images separately. Kannada, multiline text and spreadsheet-formula safety are supported. No emails are sent automatically. The guest sign-in screen explains that hosts can use the Google name/email to send wedding memories.

Apply **`supabase/migrations/0015_guest_memory_directory.sql`** after the existing migrations, then deploy the app. Existing emails are read from Supabase Auth through event-checked host-only RPCs; no secret key, Gmail inbox permission, public email list or duplicate email database is added. Existing Google accounts with wedding sign-in, invitation, family or owned-post evidence are included even if they have not posted. Photos lacking an original account ID are not assigned by matching display names; deleted accounts/content cannot be recovered. Recorded sign-in times start with analytics tracking; the migration preserves the first timestamp and records future sign-ins. These are recorded sign-ins/posts, not a full browsing history. The demo does not invent Google accounts/emails. Run `npm.cmd run test:access`, `npm.cmd run test:memories` and `npm.cmd run test:analytics`; browser checks use local fixtures. See [Supabase's user-data guidance](https://supabase.com/docs/guides/auth/managing-user-data) for the protected Auth schema.

**Simple web analytics:** **Admin → Analytics** shows unique link visitors, guests signed in with Google, and photo posts/wishes, followed by the 20 most recent posts with guest names, thumbnails and wish text. On mobile it is in **More**. Apply `0013_wedding_analytics.sql` before deployment. Visits are counted once per browser across guest pages, including `/`, without creating anonymous Auth users. Earlier visits cannot be recovered; existing verified guest sign-ins and posts are included. A carousel counts as one photo post. Host accounts are excluded from the sign-in total. Tracking failures never block guests. The demo shows this browser's visits and posts; Google sign-in counts require Supabase. Analytics reads are host-only; no personal invite tokens or URLs are saved.

**Delete a family:** hosts can use **Admin → Families & invites → Delete**, then confirm the named family. This permanently removes its members, RSVP/travel/stay details, linked devices and personal invite link. Shared photos and wishes remain. Existing host-only database policies and cascading foreign keys handle removal; no additional migration is needed. The browser demo follows the same behavior. Run `npm.cmd run test:families` with the local dev server on port 5175 (or set `WEDDING_TEST_ORIGIN`) for desktop/mobile confirmation and demo cleanup checks; `npm.cmd run test:access` verifies database permissions and cascading cleanup.

**Host password recovery:** `/admin` includes **Forgot password?** for owners and hosts. Apply migration `0012_host_password_recovery.sql`, deploy the host recovery Edge Function, and allow the reset URL in Supabase using [the setup instructions](docs/HOST-PASSWORD-RECOVERY.md). Guest accounts do not receive emails from this recovery endpoint. Run `npm.cmd run test:recovery` for mocked recovery checks.

**Feed and Create Post:** photos and approved wishes share `/invitation/feed`, newest first. `/invitation/create` offers Send a Wish or Upload Photos (up to 10 images in one carousel). Google sign-in returns to the selected page, form, quest and section. Existing hosts retain email/password access. Before deployment, apply `0010_photo_posts.sql` after `0009_google_guest_access.sql` and configure the custom domain/callbacks using [the setup guide](docs/GOOGLE-SIGN-IN.md).

**Import phone contacts:** in **Admin → Families & invites**, choose **Import contacts**. Existing family names and phone numbers, and duplicates within the selection, are skipped. Unprefixed 10-digit numbers use +91; international numbers can be reviewed and edited. Each new family starts with one contact, all wedding events, and a capacity of 6; use Edit to add family members or change these settings. Native picking depends on [browser support](https://developer.mozilla.org/en-US/docs/Web/API/Contact_Picker_API) and HTTPS.

**Family onboarding:** `/rsvp` now shares consistent responsive cards, labelled fields, readable buttons and spacing with the RSVP steps. PIN lookup, finding/joining a family and host access requests support form submission from the keyboard. Back controls preserve entries, and pending submissions prevent repeated requests. Arrival, accommodation, review and saved-reply pages use matching mobile controls. Run `npm.cmd run test:contacts` with the local server on port 5175 for mocked contact selection, contact-file parsing, duplicate checks, cancellation, save failures/retry and the full onboarding flow at 320px, 390px and desktop widths. Review screenshots are saved in `artifacts/contacts-*` and `artifacts/onboarding-*`; the native phone picker is simulated in these desktop Chrome checks.

## Run locally

Requires Node.js 20.19+ or 22.12+.

Double-click `START-WEDDING.cmd` to start the website and open it in your browser, or use the terminal commands below.

```powershell
git clone https://github.com/anandsullad77/anandwedsusmita.git
cd anandwedsusmita
npm.cmd install
npm.cmd run dev
```

Open the Local URL printed by Vite. `npm.cmd` works in PowerShell even when execution of `npm.ps1` is disabled.

```powershell
npm.cmd run build
npm.cmd run preview
```

The production website is generated in `dist/`. Latin font subsets are bundled locally; no Google Fonts connection is required. Cormorant Garamond is used for display text, with Noto Sans for body copy.
